# ParkShare security review: 2026-10 (T5.2)

Scope: `main` at `a59d0ca` (after the T4.6 merge; branch `Naumaan/t5-2-security` was cut there). This was a review only, and no code changed. I read every route under `src/app/api/**`, `src/proxy.ts`, `src/server/**` (http, auth, payments, refunds, payouts, bookings, availability, sessions, cancellations, disputes, monthly, listings, search, reviews, reports, notifications, users, admin), the admin layout and pages, the sign-in flow, `src/contracts/registry.ts`, and PRD §6, §9, FR-01, FR-06 and Appendices A and B. `docs/API.md` is generated from the registry. Its 68 rows match the registry exactly (method, path and auth: 5 public, 42 user, 21 admin). A throwaway script (untracked, `tmp/regcheck.mjs`) checked each registry entry against its route file's `auth` mode, `withIdempotency`, and `rateLimit`.

## Summary

| Severity | Count |
| -------- | ----- |
| Critical | 0     |
| High     | 1     |
| Medium   | 3     |
| Low      | 11    |

There are no Critical findings. Authorization is consistent: every route uses the `route()` wrapper with the auth mode the registry declares, and every object fetched by id is scoped to its owner, renter or host, or returns 404. The two exceptions are the Razorpay webhook (HMAC) and cron (Bearer), which skip the wrapper by design. Payment confirmation, webhook verification and dedupe, payout claiming, and the refund ceiling are all sound.

The worst problem is financial correctness rather than access control. Refunds always target the *newest* captured payment on a booking. After an extension or a duplicate capture, a cancellation refunds the wrong payment, or refunds nothing, while the booking is still cancelled (H1). The Medium findings are:

- Suspended users and rejected hosts keep bookable listings.
- Magic-link sign-in has no rate limit.
- An extension quote can be redeemed as a standalone hold at the delta price.

## Findings

### H1: Cancellation and dispute refunds only consider the newest captured payment

- **Where:** `src/server/cancellations/service.ts:19-31` (`refundablePayment`, `orderBy: { createdAt: "desc" }`, `take` first). It is used by `cancelBooking` (`:75-98`) and by `resolveDispute` (`src/server/disputes/service.ts:255`).
- **Problem:** A booking can carry more than one captured `Payment`:
  - an extension order (`requestExtension`, `src/server/sessions/service.ts:338`, with `EXTENDABLE` including `CONFIRMED` at `:50`), or
  - a duplicate capture that `settleTx` stores as `CAPTURED_UNFULFILLED` and auto-refunds in full (`src/server/payments/service.ts:349-377`).

  `refundablePayment` picks the newest row, and the refund amount (and, for renters, the policy base `paidPaise`) is computed from that row alone.
- **Exploit or failing scenario:**
  1. *Extension, then host cancel.* A renter books a CONFIRMED slot starting tomorrow for ₹400 and extends it by an hour for ₹100 (allowed before start). The host then cancels with `POST /api/bookings/:id/cancel`. `refundablePayment` returns the ₹100 extension payment, so the renter is refunded ₹100. The ₹400 is kept even though the booking is `CANCELLED`, and host earnings are never payable because payouts need `COMPLETED`.
  2. *Duplicate capture, then any cancel.* The renter pays the same order twice (two tabs). The second capture is `CAPTURED_UNFULFILLED` and fully auto-refunded. A later cancel picks that row: `refundablePaise = 0`, so `amountPaise = 0` and no refund is created. The booking moves to `CANCELLED`, and the original ₹400 `SUCCEEDED` payment is never refunded. Nothing errors.
  3. *Admin dispute.* After either case, `resolveDispute` with `refundPaise` greater than the newest payment's amount fails with `refund_exceeds_captured`. Support cannot refund the main payment from the console.
- **Impact:** Customer funds are silently kept on cancelled bookings (FR-10, PRD §6 "refund the eligible captured amount"). The ceiling invariant "never refund more than captured" still holds. This is under-refunding, not over-refunding.
- **Minimal fix:**
  - Compute the refundable amount across all `SUCCEEDED` payments on the booking. Ignore `CAPTURED_UNFULFILLED`, which already has its own auto-refund.
  - Allocate the refund across those payments (newest first, each capped at its own `amountPaise − non-failed refunds`), with one `createRefundTx` per payment and keys such as `cancellation:${id}:${paymentId}`.
  - For the renter tier, use the sum of `SUCCEEDED` amounts as `paidPaise`.
  - Add a test for each of the extension and duplicate-capture cases.

### M1: Suspending a user or rejecting a host leaves their listings published and bookable

- **Where:**
  - `adminSuspendUser` (`src/server/admin/service.ts:212`) only sets `suspendedAt` and deletes sessions.
  - `adminVerifyHost` (`:202`) and `setHostVerification` (`src/server/listings/service.ts:66`) only change `hostVerificationStatus`.
  - Search (`src/server/search/service.ts`, `l.status = 'PUBLISHED'`), `createQuote` (`src/server/pricing/quotes.ts:23`) and `createHold` (`src/server/availability/service.ts:244`) check only the listing's own status. They never check the host's suspension or verification.
- **Exploit scenario:** An admin suspends a fraudulent host after reports. The host's listings stay in `GET /api/listings`, renters can still quote, hold and pay, and the money flows to a booking the host will never honour. The same applies to a host moved to `REJECTED`. FR-01 AC2 says unverified hosts must not have bookable listings.
- **Minimal fix:**
  - In the same transaction as the suspension or rejection, move the user's `PUBLISHED` listings to `SUSPENDED` with reason `host_suspended` (or `host_unverified`). Audit it.
  - Alternatively, or as well, add `JOIN "User" u ... u."suspendedAt" IS NULL AND u."hostVerificationStatus" = 'VERIFIED'` to search, and the same check to `createQuote` and `createHold`.
  - Decide whether existing CONFIRMED bookings get cancelled with a refund. That is a product call.

### M2: Magic-link sign-in has no rate limit (email bombing, provider cost)

- **Where:** the server action `sendLink` (`src/app/(auth)/sign-in/page.tsx:18`) and Auth.js's own `POST /api/auth/signin/resend` (`src/app/api/auth/[...nextauth]/route.ts`). Neither path goes through `route()`/`rateLimit`, and Auth.js has no built-in throttle. PRD §9 requires rate-limiting authentication.
- **Exploit scenario:** A script loops `POST /api/auth/signin/resend` with a CSRF token from `/api/auth/csrf` and `email=victim@example.com`, or submits the server action repeatedly. Every request sends a Resend email. This floods the victim's inbox, uses up the Resend quota and sender reputation, and lets anyone grow the `VerificationToken` table without limit.
- **Minimal fix:**
  - In `sendLink`, call `rateLimit("auth.email:" + email, 5, 3600)` and `rateLimit("auth.ip:" + ip, 20, 3600)` before `signIn`, and redirect to the same "check your email" state when either limit is hit (no enumeration oracle).
  - Block direct `POST /api/auth/signin/*` by wrapping `handlers.POST`: rate-limit it the same way, or reject it unless it comes from the server action.

### M3: An extension quote can be redeemed as a standalone booking at the delta price

- **Where:**
  - `requestExtension` (`src/server/sessions/service.ts:390`) writes an ordinary `PriceQuote` for `[b.endAt, newEndAt]`. Its totals are the *delta* `price(start→newEnd) − price(start→end)`, under the original booking's policy version.
  - `holdFromQuote` (`src/server/bookings/service.ts:188-206`) accepts any unexpired quote the caller owns. Nothing marks a quote as an extension.
  - `turnoverBufferMinutes` defaults to 0 (`prisma/schema.prisma:326`), and `blockedRange` is `[)`. The new hold therefore sits directly after the renter's own booking without overlapping it.
- **Exploit scenario:**
  1. A renter with an HOURLY booking of 1 h 30 min (billed as 2 h because hours are rounded up, `src/server/pricing/calc.ts:77`) calls `POST /api/bookings/:id/extend` with `newEndAt = end + 90 min`. The quote is 3 h − 2 h = **1 h**.
  2. They skip paying the extension order and call `POST /api/bookings/hold { quoteId }`. The result is a separate 90-minute booking billed as 1 hour (a standalone booking would be billed 2 h), at the old commission and fee.
  3. With WEEKLY or DAILY caps the gap can be larger.

  The client still never sends an amount, but the server prices the booking from the wrong formula. This bends the PRD §6 invariant that the client must not influence the amount.
- **Minimal fix (no migration):** In `holdFromQuote`, and in `validateQuote` so `createHold`'s other callers are covered too, reject the quote with the same `quote_invalid` 422 if any `Payment` row has `extensionQuoteId = quoteId`. This covers every way a client can learn an extension quote id:
  - With Razorpay configured, `createExtensionOrder` writes that Payment row inside `requestExtension` before the response returns.
  - With Razorpay unconfigured, the extend route returns `notConfigured()` without the body (`src/app/api/bookings/[id]/extend/route.ts`), so the quote id never reaches the client.
  - A zero-total extension is applied at once, and the booking's new range then blocks any reuse through the overlap constraint.

  Do **not** reject quotes merely because `startAt` equals one of the caller's booking `endAt`s: that also blocks legitimate back-to-back bookings made through `POST /api/quotes`. If a migration is allowed later, a `PriceQuote.kind` / `extensionOfBookingId` column is the cleaner long-term fix.

### L1: Report evidence URL check is loose (any Cloudinary cloud, `http:`, fetch URLs)

- **Where:** `src/server/reports/service.ts:9-19` (`isAllowedEvidenceUrl`). It accepts `http:` and any `res.cloudinary.com/<any-cloud>/...` URL whose path merely *contains* `/listings/` or `/evidence/`, which includes `/image/fetch/https://evil/.../listings/x`. The links are rendered as clickable `<a href>` in `src/app/admin/reports/page.tsx:267-273`.
- **Scenario:** A user files a report with `https://res.cloudinary.com/attacker/image/upload/listings/phish.svg`, or a fetch-proxy URL. An admin clicks "Evidence #1" and lands on attacker-controlled content. This is not XSS on the app origin (React 19 also blocks `javascript:`), but it is a phishing and tracking vector aimed at admins.
- **Fix:** Use the same strict check as `isEvidenceUrl` in disputes (`src/server/disputes/service.ts:39`): `https` only, our `CLOUDINARY_CLOUD_NAME`, `/image/upload/(v\d+/)?`, an owned folder, and an image extension.

### L2: Test and e2e overrides are gated by a NODE_ENV denylist

- **Where:**
  - `src/server/payments/provider.ts:151` honours `RAZORPAY_API_URL` whenever `NODE_ENV !== "production"`.
  - `setPaymentProvider` (`:136`) and `setEmailSender` (`src/server/notifications/email.ts:43`) are exported without a guard.
  - `npm run worker` (`src/server/jobs/worker-cli.ts`), which runs refunds and reconciliation, does not set `NODE_ENV`.
- **Scenario:** A production worker started without `NODE_ENV=production`, with a stray `RAZORPAY_API_URL` in its env, sends refund and capture calls (with the live key secret in Basic auth) to that host. That leaks the secret and accepts fake provider answers. AGENTS.md says fake payment behaviour may exist only under `NODE_ENV=test`.
- **Fix:** Use an allowlist: `NODE_ENV === "test" || NODE_ENV === "development" ? RAZORPAY_API_URL : undefined`. Have `setPaymentProvider` and `setEmailSender` throw unless `NODE_ENV === "test"`. Set `NODE_ENV=production` in the worker's deploy docs or script.

### L3: Rate-limit identity is spoofable for anonymous callers, and some write paths have no limit

- **Where:** `clientIp` (`src/server/http/route.ts:43-45`) trusts the first `X-Forwarded-For` entry. No limits exist on `POST /api/reviews`, `/api/bookings/:id/incidents`, `/api/listings` (create), `/api/bookings/:id/cancel`, or `/api/me/vehicles`.
- **Scenario:** `GET /api/listings` (120/min per IP) is bypassed by rotating `X-Forwarded-For: <random>`, which allows scraping or loading the search query. Behind Vercel the platform overwrites the header, but on any other proxy it passes through.
- **Fix:** Take the IP from the platform header (`x-real-ip` / `x-vercel-forwarded-for`) or the *last* trusted hop. Add modest per-user limits to the write routes listed above.

### L4: No security headers (clickjacking of the admin console, no HSTS or CSP)

- **Where:** `next.config.ts` has no `headers()`, and `src/proxy.ts` sets none.
- **Scenario:** An attacker frames `/admin/users` on their own site and tricks a signed-in admin into clicking "Suspend" or "Verify". SameSite=Lax cookies are sent on top-level navigations but not inside cross-site iframes in modern browsers, so the risk is reduced, not removed (older browsers, and same-site subdomains).
- **Fix:** Add `X-Frame-Options: DENY` / `Content-Security-Policy: frame-ancestors 'none'`, `Strict-Transport-Security`, `Referrer-Policy: strict-origin-when-cross-origin`, and `X-Content-Type-Options: nosniff` via `headers()` in `next.config.ts`.

### L5: Env validation does not run at boot and accepts placeholder secrets

- **Where:** `src/lib/env.ts` is imported only by `src/app/api/cron/tick/route.ts`. Elsewhere `process.env.X!` is read directly, for example `AUTH_URL` in `route.ts:39`. Placeholders such as `AUTH_SECRET="replace-me"` and `CRON_SECRET="replace-me"` from `.env.example` pass `min(1)`.
- **Scenario:** A deploy copies `.env.example`. The app boots, and the cron endpoint accepts `Authorization: Bearer replace-me`, so anyone can run the job queue at will.
- **Fix:** Import `env` from `src/instrumentation.ts` (or `next.config.ts`) so a bad config fails at startup. In production, require `AUTH_SECRET` and `CRON_SECRET` of at least 32 characters that are not `replace-me`, and require the provider keys.

### L6: `createHold` does not re-check that the listing is still PUBLISHED

- **Where:** `src/server/availability/service.ts:240-245` checks only `if (!listing)`. The status check lives only in `createQuote` (`src/server/pricing/quotes.ts:23`).
- **Scenario:** An admin suspends a listing. For up to 15 minutes (`QUOTE_TTL_MS`), anyone holding a quote can still hold and pay for it.
- **Fix:** Inside the transaction, use `if (!listing || listing.status !== "PUBLISHED") throw unprocessable("listing_unavailable", …)`.

### L7: Exact address, access instructions, and host phone and email stay visible indefinitely

- **Where:** `ACCESS_STATUSES` (`src/server/bookings/service.ts:29-36`) includes `COMPLETED` and `DISPUTED`, and `access` is built at `:137-146`.
- **Scenario:** A renter who parked once a year ago still sees the gate code and the host's phone number on `/bookings/:id`. PRD §9 says to reveal these only when necessary.
- **Fix:** Show `access` to the renter only from CONFIRMED to OVERSTAY, and for a short window after `checkedOutAt` (for example 24 h). Hosts always see their own listing.

### L8: The webhook dedupe key (`x-razorpay-event-id`) is not covered by the signature

- **Where:** `src/app/api/webhooks/razorpay/route.ts:20`. The HMAC covers only the body.
- **Scenario:** Anyone who captured one signed webhook can replay the body with new event ids. Each replay passes dedupe. The effects are idempotent:
  - `settleTx` returns `already_settled`.
  - Refund outcomes are terminal.
  - `payment.failed` only touches `ORDER_CREATED`/`PENDING` rows.

  The worst case is a replayed old `payment.failed` marking a newer open attempt on the same order `FAILED`. The renter can retry, so impact is low.
- **Fix:** Also dedupe on a body-derived key, for example `sha256(raw)` or `(event, payload.payment.entity.id)`. Optionally reject events whose `created_at` is older than a few days.

### L9: Unvalidated pagination cursors return 500 instead of 400

- **Where:** `PaginationQuery.cursor` is any string (`src/contracts/common.ts:22`). `listListingReviews` (`src/server/reviews/service.ts:114`, a **public** route) and `listReports` (`src/server/reports/service.ts:157`, admin) pass it to Prisma without the UUID check other services do.
- **Scenario:** `GET /api/listings/<id>/reviews?cursor=x` returns a 500 and logs an "unhandled" error. Anonymous callers can generate error-log noise and trip 5xx alerts.
- **Fix:** Use `if (cursor && !Uuid.safeParse(cursor).success) throw new HttpError("validation_error", "Invalid cursor")`, as `listBookings` does.

### L10: Dependency audit: 7 high in `braces`, via the `shadcn` CLI listed under `dependencies`

- **Where:** `package.json:47` lists `"shadcn": "^4.22.0"` under `dependencies`. `npm audit --omit=dev` reports 7 high, all GHSA-vfj7-8cjw-p6xm (braces ReDoS/stack exhaustion), through `shadcn → fast-glob → micromatch → braces` and `ts-morph`.
- **Impact:** Not reachable at runtime, because the app never imports the shadcn CLI. It does add noise to prod installs and audits.
- **Fix:** Move `shadcn` to `devDependencies`. Don't run `audit fix --force`, which downgrades shadcn to 1.0.0.

### L11: Booking-confirmed and payout-failed notifications are still log stubs, and the payout stub logs free text

- **Where:** `src/server/payments/notify.ts:14` and `src/server/payouts/notify.ts:15` still only `log("info", "notification.pending_t2_6", { userId, type, ...payload })`, even though `notify()` exists in `src/server/notifications/index.ts`.
- **Impact:**
  - `BOOKING_CONFIRMED_*` and `PAYOUT_FAILED` never reach users. This is a functional gap that the coordinator will want closed.
  - The payout stub writes the admin's free-text `reason` (which may contain bank or PII details) to stdout, against PRD §9 "no sensitive information in logs".
- **Fix:** Replace both stubs with `notify(userId, type, payload, { idempotencyKey })`, as the TODO already says, and drop `reason` from any log line.

## PASS list by checklist item

**1. Authorization / IDOR:** PASS apart from H1, M1 and M3 (see the matrix).
- Every handler that fetches by id scopes to owner, renter or host, or returns 404.
- Admins act only through `/api/admin/**`.
- Strict zod objects stop mass assignment of `status`, `hostId`, `roles` and `approx*`.

**2. Privacy:** PASS.
- Public listing, search and review responses go through strict schemas: approx coords on a ~300 m grid, no address, no access instructions, host id, name and `verified` only, reviewer first name only.
- Search filters on approximate columns, and the exact-column prefilter margin (0.0016°) is wider than the grid error (0.0015°). Probing viewport edges therefore cannot pin down the exact location.
- Exact address, coords, instructions and host contact appear only in `BookingDetail.access`, for the renter or host of a committed booking (see L7 for retention).
- Notification previews carry no address, phone or amounts, and email HTML is escaped.
- Request logs record method, path, status and userId only. The magic-link URL is printed only by the dev console sender, and that sender throws in production.

**3. Payments:** PASS.
- Order amounts come from the `Booking` and `PriceQuote` snapshots, never from the client. `hostId` is derived server-side.
- The callback needs a valid signature, ownership of the payment row by booking and renter, and a provider fetch matching order, amount and currency.
- Webhook verification is HMAC over the raw body (`req.text()`) using `timingSafeEqual` with a length check. The `ProviderEvent` insert (`ON CONFLICT DO NOTHING`) and every effect run in one transaction.
- `RAZORPAY_API_URL` is ignored under `NODE_ENV=production` (see L2 for hardening).
- `createRefundTx` locks the Payment row and enforces amount ≤ captured − non-failed refunds.
- Payouts lock bookings `FOR UPDATE` in id order, require COMPLETED, unclaimed and PAYABLE, and claim them through `hostPayoutId`. `mark-paid` and `mark-failed` lock the payout and are idempotent.
- No mock-success path is reachable in production: `setPaymentProvider` is only called from tests.

**4. Web:** PASS apart from L1, L3 and L4.
- *CSRF:* every mutating `/api` route goes through `route()` → `assertSameOrigin`. Exceptions are the webhook (HMAC), cron (Bearer) and Auth.js (own token). Server actions get Next's Origin check, and cookies are SameSite=Lax.
- *XSS:* no `dangerouslySetInnerHTML` anywhere in `src`. Reviews, reports and descriptions render as React text.
- *Open redirect:* `safeCallback` allows only `/` paths not followed by `/` or `\`, and Auth.js's redirect callback stays same-origin.
- *SQL injection:* no `$queryRawUnsafe` or `$executeRawUnsafe`. Every `Prisma.raw` takes a value from a fixed map or a zod enum (price column, amenities, dimension columns, sort key).
